# エンドツーエンド暗号化（E2EE）とローカルモードの設計

デスクトップ版の実装（`desktop/src/main/crypto.ts`、`encryptionService.ts`）と、これから実装する Android 版の共通の仕様。
決定の経緯は `_docs/claude_logs/2026-10-23_privacy-local-mode-e2ee-history.md`（Q1〜Q26）にある。

## 1. 目的と前提

- Firebase プロジェクトの所有者（開発者）でも、ほかの利用者のタスク名・メモを Firebase コンソールで読めないようにする。
  セキュリティルールでは所有者の閲覧を防げないため、端末の中で暗号化してから送る。
- 守る相手は「クラウド側でデータを見る人」。PC やスマホを直接操作できる人は対象外（ローカルモードの `store.json`
  も平文のまま。Q10）。
- 保存先は起動時に選ぶ。「この PC だけで使う」（ローカルモード、外部に送信しない）か、「Google でログインして同期」
  （暗号化は必須。Q7）。

## 2. 暗号化する項目

| ドキュメント        | 暗号化する               | 平文のまま                                                             |
| ------------------- | ------------------------ | ---------------------------------------------------------------------- |
| `tasks/{id}`        | `name`、`memo`（空は空） | 分類、完了・削除フラグ、日時、累計分数・回数、`sortOrder`、`updatedBy` |
| `sessions/{id}`     | `taskName`               | `taskId`、日時、分数、`endReason`、`device`                            |
| `state/desktop`     | `currentTaskName`        | 状態、日時、`device`                                                   |
| `state/preferences` | （なし。タスク ID だけ） | すべて                                                                 |

平文の項目は、保守に必要な最小限のメタデータとして開発者が見えることを受け入れている（Q5）。文字数は暗号文の長さから
おおよそ分かる（パディングしない。Q9）。

## 3. 鍵の構成（エンベロープ暗号化）

```
タスク名・メモ ──AES-256-GCM──▶ 暗号文（Firestore）
                      ▲
                データ鍵 DEK（アカウントごとに 1 つ、ランダム 32 バイト、変更しない）
                      ▲ ラップ（AES-256-GCM）
        ┌─────────────┴─────────────┐
  KEK = PBKDF2(パスフレーズ)    KEK = HKDF(回復キー)
```

- DEK はアカウント作成時（最初の PC での暗号化の設定）に 1 回だけ作る。パスフレーズの変更や回復キーの再発行では
  DEK を「包み直す」だけで、タスクを暗号化し直さない。ほかの端末は保持している DEK でそのまま使える。
- パスフレーズと回復キーのどちらでも DEK を取り出せる。両方なくすとデータは復元できない（管理者がクラウドのデータを
  削除し、やり直す）。

## 4. 形式

### 4.1 暗号文

```
"e1:" + base64( iv[12 バイト] ‖ 暗号文 ‖ 認証タグ[16 バイト] )
```

- AES-256-GCM。IV は暗号化のたびに乱数で 12 バイト作る（**同じ鍵で IV を再利用しない**）。AAD は使わない。
- 標準の base64（`+` `/`、パディング `=` あり）。平文は UTF-8。
- `iv ‖ 暗号文 ‖ タグ` は Web Crypto と Android の `Cipher.getInstance("AES/GCM/NoPadding")` の出力（タグは末尾）と
  同じ並び。Android は IV を先頭に付けるだけでよい。
- 先頭の `e1:` は形式のバージョン。将来形式を変えるときは `e2:` にする。
- 空のメモは `""` のまま送る。読むときに `e1:` で始まらない値は平文として扱う（暗号化より前のデータ）。
- 復号できない値（改ざん、別の鍵）は例外にせず、「（読み取れません）」と表示する。

### 4.2 鍵ドキュメント `users/{uid}/state/keys`

```jsonc
{
  "v": 1,
  "passphrase": {
    "kdf": "PBKDF2-SHA256",
    "iterations": 600000,
    "salt": "<base64, 16 バイト>",
    "wrappedKey": "e1:…", // DEK を KEK(パスフレーズ) で 4.1 の形式に暗号化したもの
  },
  "recovery": {
    "kdf": "HKDF-SHA256",
    "salt": "<base64, 16 バイト>",
    "wrappedKey": "e1:…", // DEK を KEK(回復キー) で暗号化したもの
  },
  "updatedAt": "<serverTimestamp>",
}
```

- ソルトはパスフレーズ用と回復キー用で別にする（パスフレーズの変更で回復キーが使えなくならないように）。
- KDF の名前と回数を一緒に保存しているので、将来 Argon2 などに変えられる（Q12）。
- 作成は Firestore のトランザクションで行い、すでにあれば失敗させる。キャッシュが古い端末が別の端末の鍵を上書きすると、
  すべてのデータが読めなくなるため。削除はルールで禁止。

### 4.3 パスフレーズ → KEK

- 10 文字以上（コードポイントで数える）、文字種の条件なし（NIST SP 800-63B。`src/shared/passphrase.ts`）。
- **Unicode NFC に正規化してから** UTF-8 にする（同じ日本語でも OS や IME で合成形・分解形が変わるため）。
- PBKDF2-HMAC-SHA256、`iterations` 回（新規は 600,000）、出力 32 バイト。Android は `SecretKeyFactory`
  （`PBEKeySpec` は文字の配列を受け取り、バイト列への変換が実装に任される）を使わず、`Mac("HmacSHA256")` で
  RFC 8018 のとおりに書き、NFC で正規化した UTF-8 のバイト列をそのまま入れる（`android/.../crypto/E2ee.kt`）。

### 4.4 回復キー → KEK

- 乱数 20 バイト（160 ビット）を Crockford base32（`0123456789ABCDEFGHJKMNPQRSTVWXYZ`）で 32 文字にし、4 文字ずつ
  8 組をハイフンでつなぐ（例：`K7QM-2XRT-P9DW-H4NA-VC3E-J8KZ-R6FY-T2GB`）。
- 入力は大文字に変え、ハイフンと空白を取り除き、`O` → `0`、`I`・`L` → `1` と読む。32 文字でない、または表にない文字
  （`U` など）を含む場合は「回復キーが正しくありません」。
- デコードした 20 バイトを入力に HKDF-SHA256（salt = `recovery.salt`、info = `"shiodoki recovery v1"`、出力 32 バイト）。
  すでに十分ランダムなので遅い KDF は使わない。Android には標準の HKDF がないため、`Mac("HmacSHA256")` で
  RFC 5869 の Extract と Expand（1 ブロック）を実装する。

### 4.5 端末での DEK の保持

- デスクトップ：Electron `safeStorage`（Windows DPAPI、macOS キーチェーン、Linux libsecret / kwallet）で暗号化して
  `userData/dek.bin` に保存する。中身は `{ uid, key }` で、別のアカウントでは使わない。ログアウトで削除する。
  Linux でキーリングがない場合（`basic_text`）も保存する（1 の前提のとおり、PC を直接操作できる人は対象外）。
  `safeStorage` が使えない場合はメモリにだけ持ち、起動のたびにロック解除する。
- Android：Android Keystore で保護して保存する（Q11）。
- DEK はデスクトップのメインプロセスの外に出さない。画面（renderer）はパスフレーズを渡して回復キーを受け取るだけ、
  Firebase SDK を動かす data ウィンドウは暗号文しか見ない。

## 5. 画面の流れ（デスクトップ）

| 場面                           | 動作                                                                                                   |
| ------------------------------ | ------------------------------------------------------------------------------------------------------ |
| 初回起動・ログアウト後         | 「データの保存先」。選択は `settings.json` の `storage`（`local` / `cloud`）。`TIMER_LOCAL=1` が優先   |
| この PC だけで使う             | `storage: local` にして再起動。トレイの「Google でログインして同期…」で `cloud` にして再起動できる     |
| ログイン（鍵ドキュメントなし） | 暗号化の設定：パスフレーズ（1/2）→ 回復キーを保存（2/2）→ この PC のローカルデータのコピー（D-07）     |
| ログイン（鍵ドキュメントあり） | ロック解除：パスフレーズか回復キー。間違いはその場で表示                                               |
| 2 回目以降の起動               | 保持している DEK で、そのままタスク選択画面へ                                                          |
| 設定・解除の画面を閉じる       | ログアウト（鍵がないままログインした状態は作らない）                                                   |
| オフラインで鍵が読めない       | 「インターネット接続が必要」と表示し、再試行・ログアウト・終了を選ぶ                                   |
| トレイ「暗号化…」              | パスフレーズの変更（現在のパスフレーズか回復キーで確認）、回復キーの再発行（今の回復キーは無効になる） |
| ログアウト                     | DEK と端末内のキャッシュを削除し、`storage` を未選択に戻す                                             |

## 6. セキュリティルール

`firebase/firestore.rules`：

- `name`、`taskName`、`currentTaskName`：`^e1:[A-Za-z0-9+/]+={0,2}$` に一致し、1,000 文字以下。
- `memo`：`""` か、同じ形式で 21,000 文字以下。
- 上限はアプリの上限（タスク名 200、メモ 5,000 文字）の最悪の暗号文の長さ：UTF-16 の 1 単位を UTF-8 で 3 バイト、
  ＋IV 12 ＋タグ 16 バイト、base64 で 4/3 倍、＋接頭辞。
- `state/keys`：本人だけ読み書きでき、§4.2 の形だけを受け付ける（PBKDF2 は 100,000 回以上）。削除できない。

## 7. 移行と公開の順序

ルールを公開すると、平文で書く古いアプリ（暗号化に対応する前の Android 版を含む）は書き込めなくなる。既存の平文の
タスクも、別の項目を更新した時点でルールに弾かれる。Kazi のデータは移行せず作り直す（Q8）：

1. Android 版を E2EE に対応させる。
2. クラウドのデータをバックアップする（`firebase/scripts/backup.mjs`、手順は `firebase/README.md`。タスクとセッションを
   `store.json` の形式で）。
3. クラウドのデータを削除し、ルールを公開する（`cd firebase && npm run deploy:rules`）。
4. 新しいデスクトップ版と Android 版を入れ、デスクトップでバックアップをローカルモードとして置いてからログインし、
   初回のコピーで暗号化して再アップロードする。

## 8. 制限と受け入れたリスク

- メタデータ（§2 の平文の項目）と、名前・メモのおおよその長さは開発者に見える。
- 開発者は暗号文を消したり、タスク間で入れ替えたりはできる（AAD でドキュメント ID に結び付けていないため）。読むことは
  できない。
- 鍵ドキュメントを消せるのも開発者だけ（ルールで利用者の削除は禁止）。
- パスフレーズの強さは利用者次第（PBKDF2 600,000 回で総当たりを遅くしているだけ）。
